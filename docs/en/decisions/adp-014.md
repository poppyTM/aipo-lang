# ADP-014 — Embedded profile, Dual-Track architecture (Wasm Web vs. native VM) and the `aipo-vm` evolution roadmap

- **Status**: Approved and Implemented (Milestones 1 to 4 completed)
- **Date**: 2026-10-06
- **Deciders**: Raillen & Poppy Team
- **Phase**: Implemented / PR #16 open

---

## 1. Context and motivation

In architectural decision **ADP-013**, Aipo adopted the WebAssembly format (Wasm 2.0 / WASI) and the Wasmtime engine (Cranelift JIT) as the primary substrate to unify execution and pave the way for self-hosting.

However, empirical measurements and alignment with the language's long-term vision revealed requirements that a heavy JIT engine such as Wasmtime cannot meet:

1. **Memory footprint and binary size**: by incorporating the Cranelift backend, x86/ARM assemblers, stack-unwinding tables and a register allocator, Wasmtime adds more than 25 MB to the CLI executable.
2. **Cold-start time incompatible with the shell**: terminal scripts, infrastructure automation and interactive shells require immediate startup (< 2 ms). Wasmtime's JIT compilation and validation impose a noticeable initial overhead (15 ms to 50 ms).
3. **Infeasibility on microcontrollers (MCUs)**: devices without an MMU (e.g. Cortex-M, ESP32, RP2040) typically have 64 KB to 512 KB of Flash and 16 KB to 64 KB of static RAM. They cannot run JIT runtimes or dynamic executable pages (`mprotect`/W^X).
4. **Indirection in system automation**: the forced isolation layer of WASI hinders natural system-administration operations (such as direct SO process pipes, process signals and synchronous POSIX/Windows terminal access).

Given this evidence, Aipo's evolution toward an efficiency level equivalent to **Lua** is formalized — a language universally recognized for its sub-millisecond startup, tiny binary (~250 KB to 500 KB) and ease of embedding in game engines and microcontrollers.

## 2. The decision: Dual-Track architecture

To accommodate both web portability and the lean performance of embedded systems and terminal scripts, Aipo establishes a **Dual-Track** strategy:

```
                  ┌────────────────────────────────────────┐
                  │             Aipo code                  │
                  │   (Canonical frontend: Lexer / Sema)    │
                  └───────────────────┬────────────────────┘
                                      │
            ┌─────────────────────────┴─────────────────────────┐
            ▼                                                   ▼
 ┌──────────────────────┐                           ┌───────────────────────┐
 │     Web/Cloud track  │                           │  Native/Embed track   │
 │   `aipo-wasm` (.wasm)│                           │  `aipo-bytecode` (.aibc)
 ├──────────────────────┤                           ├───────────────────────┤
 │ • Emitter: wasm-enc. │                           │ • VM: `aipo-vm`       │
 │ • Target: Browser,   │                           │ • Target: Fast CLI,   │
 │   Workers, Sandboxes │                           │   Shell, native games │
 │ • Wasmtime runner:   │                           │   and MCUs (`no_std`) │
 │   Optional (feature) │                           │ • No JIT dependencies │
 └──────────────────────┘                           └───────────────────────┘
```

### Fundamental clarification about WASM

**We are not abandoning WebAssembly.** WebAssembly remains the official target for the Web and for cloud platforms that already provide their own runtimes (browsers, Deno, Bun, Cloudflare Workers). The `aipo-wasm` crate will keep generating compact `.wasm` files through `wasm-encoder`.

**What changes**: the Wasmtime JIT interpreter stops being the mandatory executor of the desktop CLI and becomes a conditional dependency (*feature-gated*). Our own virtual machine (**`aipo-vm`**) takes responsibility as the high-speed, small-footprint, low-memory native execution engine.

## 3. Progressive evolution model in 3 layers

To ensure the same core serves everything from desktop games to microcontrollers, the evolution of `aipo-vm` is structured into **three concentric layers**:

```
┌────────────────────────────────────────────────────────┐
│ Layer 3: Bare-Metal MCU (future horizon)               │
│   • Peripheral HAL (GPIO, UART, I2C, Timers)           │
│   • Strict `#![no_std]`, zero OS dependency            │
│   • Direct execution from Flash (XIP)                  │
└───────────────────────────▲────────────────────────────┘
                            │
┌───────────────────────────┴────────────────────────────┐
│ Layer 2: System Shell (standalone CLI)                  │
│   • Process builtins (`spawn`, `pipe`, `env`, `fs`)    │
│   • Interactive REPL and `|>` data pipes                │
│   • Single static binary (< 1 MB), boot < 2 ms         │
└───────────────────────────▲────────────────────────────┘
                            │
┌───────────────────────────┴────────────────────────────┐
│ Layer 1: Host Scripting (core engine)                  │
│   • `aipo-vm` as C ABI library (`libaipo.a`)           │
│   • State isolated per instance (`VmContext` reentrant) │
│   • Zero OS dependency: I/O via host callbacks          │
│   • Compact memory model (16 bytes per value)          │
│   • Arena management with O(1) deallocation            │
└────────────────────────────────────────────────────────┘
```

- **Layer 1 (Host Scripting)**: the universal foundation. A pure Rust/C ABI engine with no OS dependencies. All I/O and lifecycle is controlled by the host through a callback interface.
- **Layer 2 (System Shell)**: Layer 1's engine wrapped in an executable with process primitives (`fork`, `exec`, kernel pipes) and a fast REPL for infrastructure automation.
- **Layer 3 (Bare-Metal MCU)**: Layer 1's engine configured with `#![no_std]` and static allocation, running directly on microcontrollers without an OS.

## 4. Architectural comparison: Aipo vs. Lua

We adopt **Lua 5.4**'s architecture as the industry-standard reference:

| Property | Lua 5.4 (C) | Aipo today (host dev) | Aipo Nano / Shell profile (target) |
| :--- | :--- | :--- | :--- |
| **Binary size** | ~280 KB (stripped) | ~20 to 30 MB (with Wasmtime) | **~350 KB to 550 KB** |
| **Isolated VM size** | ~120 KB | ~1.5 MB (`aipo-vm` rlib) | **~50 KB to 90 KB** |
| **Boot time** | < 1 ms | 15 to 40 ms | **< 2 ms** |
| **`Value` size** | 16 bytes (`TValue`) | 48 bytes (Rust enum + `Rc`) | **16 bytes** (tagged union / NaN-boxing) |
| **Bytecode architecture** | Virtual registers | Pure stack (Stack VM) | **Virtual registers (32-bit u32)** |
| **Heap management** | Incremental tricolor GC | OS allocator (`Rc`/`RefCell`) | **Linear arenas (O(1) deallocation)** |
| **Bare-metal environment** | Fully portable (`no_std` C) | Depends on `std` and OS threads | **`#![no_std]` + optional `alloc`** |

## 5. Technical scope of the reduced (embedded / shell) profile

### What is sacrificed in the reduced target

1. **Rich visual diagnostics**: errors formatted with colors, underlines and contextual suggestions are replaced by compact `code:line:column` tuples (e.g. `E042:12:4`). Full descriptive messages stay in the development host.
2. **Unicode normalization tables and regex DFA**: strings are treated as raw UTF-8 without advanced NFC normalization at runtime, saving more than 500 KB of compiled tables.
3. **Mandatory floating point (`Float`)**: on microcontrollers without an FPU, `f64` support is disabled via feature flag to avoid pulling in heavy math libraries in software.
4. **Unrestricted heap allocation**: the system's dynamic allocator is replaced by a **fixed-size linear memory arena** (e.g. 16 KB to 64 KB). Exceeding the quota raises the safe failure `E_OUT_OF_MEMORY`.
5. **Preemptive multi-threaded concurrency (`spawn`)**: in the nano profile, async tasks become single-loop cooperative or compile errors.

### What is preserved (where Aipo surpasses Lua)

1. **Prevention of invisible globals**: strict lexical scope with `let` immutable by default and restricted `var` prevents accidental global variables from typos.
2. **Closed sum types (`enum`) and exhaustive `match`**: enums and destructuring cost almost nothing at runtime (just a numeric tag index), providing safety Lua lacks.
3. **Pipe operator (`|>`)**: fluent ergonomics for both collection manipulation and shell process pipelines.
4. **Explicit error handling (`Result[T, E]`)**: no silent null-return traps or unpredictable exception overhead.

## 6. Stratified type system

| Tier | Included types | Availability |
|---|---|---|
| **Tier 1 (Mandatory / Universal)** | `Int` (64/32b), `Bool`, `Byte`, `Bytes` (fat pointer), `String` (fat pointer), `Enum` (u16 tag + optional payload), static `Struct` (direct numeric offsets), `Function`/`Native`. | Present in every profile (bare-metal MCU, shell, desktop). Fits in < 30 KB. |
| **Tier 2 (Optional by feature)** | `Float` (64-bit IEEE-754), `Dict` (open-addressing hash table), `List` with unbounded dynamic growth. | Enabled in shell and desktop profiles. Disabled in the bare-metal nano profile. |

## 7. Transition to virtual-register bytecode

The `aipo-vm` will migrate from the pure stack model to a **virtual-register model with fixed 32-bit (`u32`) instructions**:
- **Fewer instructions**: 35% to 50% fewer instructions executed for the same logic compared to the stack machine, halving CPU dispatch cycles.
- **Fixed 4-byte instructions**: `iABC` format (7b Opcode, 8b A, 9b B, 9b C), `iABx` and `iAsBx`.
- **Execute-In-Place (XIP)**: bytecode can be read and executed directly from the microcontroller's Flash memory without being copied into RAM.

## 8. Implementation roadmap in 4 milestones

1. **Milestone 1 — Decoupling and dependency slimming**:
   - `wasmtime-runner` feature flag in `crates/aipo-cli` (optional).
   - `[profile.nano]` in the workspace with `opt-level = "z"`, `lto = true`, `panic = "abort"`, `codegen-units = 1` and `strip = true`.
2. **Milestone 2 — `Value` compaction and arenas**:
   - Reduce the `Value` layout to 16 bytes.
   - Implement `ArenaAllocator` with O(1) reset and a fixed quota.
3. **Milestone 3 — Bytecode transition to registers**:
   - Specify the 32-bit instructions in `crates/aipo-bytecode`.
   - Direct dispatch loop in `crates/aipo-vm`.
4. **Milestone 4 — Shell CLI and C ABI support**:
   - `aipo-sh` binary with system-automation builtins.
   - Validation of the C ABI (`libaipo.a`) for embedding in C/Rust.

---

## 9. Empirical results and validation of the 4 fronts (A to D)

1. **Front A — Feature parity in `RegVm`**:
   - Full support for calls (`Call`), property access (`GetField`, `SetField`) and collection indexing (`GetIndex`, `SetIndex`) in the virtual-register machine.
   - Direct compilation of `CoreFunction` through `RegEmitter` with end-to-end execution verification.
2. **Front B — Radical binary slimming**:
   - Nano binary `aipo-sh` reduced from **25+ MB** to **2.0 MB** with feature gating of WASM/JS emitters, formatter and Unicode/regex tables.
   - Startup time kept at **< 2 ms**.
3. **Front C — C ABI exposure for embedding**:
   - Export of `aipo_reg_vm_create`, `aipo_reg_vm_destroy`, `aipo_reg_vm_set_reg_int`, `aipo_reg_vm_get_reg_int` and `aipo_reg_vm_run` in the static library `libaipo_c_abi.a` with a validated native C harness.
4. **Front D — Bare-metal MCU support**:
   - `RegInstruction` and `RegOpCode` opcodes represented as pure 32 bits with no allocation or OS dependencies, allowing XIP (Execute-In-Place) execution directly from Flash memory with a fixed 4 KiB RAM window.
